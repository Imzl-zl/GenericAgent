## [2026-09-13 | 生图 400 根因闭环：参数协商自愈 + 网关 120s 超时归因]

- **Events**：用户报"生图 400"并指向 `agnes-image-2.5-flash` 官方文档，问是参数问题、架构问题还是细节问题。仓库内不存在用户所述日志文件（`temp/` 只有 08-14 的测试产物），改为**真实 key 复现归因**：先 `GET /v1/models` 摸清两把 key 各自的模型集，再用 10 次最小/完整参数探测矩阵定位——① 渠道1 key（`mykey.image_gen` 原配置）**根本没有 agnes 模型** → 503 `model_not_found ... under group image (distributor)`；② 渠道2 key + agnes + 客户端原 payload → **400 `output_format is not supported by text image queue`**（与用户报的 400 一致）；③ 加 `quality=high` → **400 `quality is not supported by text image queue`**；④ 同网关 `gpt-image-2` 却**接受** `output_format` 并返回 b64_json；⑤ gpt-image-2 多次撞 **Cloudflare 524**（125s = CF proxy read timeout），而 agnes 稳定 8-11s。修复客户端 + 工具 schema + 落盘命名，真实 key 端到端闭环（默认参数单请求 9.6s 出图 1.74MB，原 400 参数集自适应通过）。
- **Changes（第二轮，同日稳定性收口）**：`tenant_platform/backend-go/internal/application/runtime_config.go` — 托管 `image_gen` 块补 `read_timeout`（`GA_IMAGE_GEN_READ_TIMEOUT` 默认 100，新增 `imageGenReadTimeout()`）+ `max_retries` 2→1（常量注释写明任务预算算术）；`runtime_config_test.go` — 新增 `TestBuildRuntimeConfigImageGenTimeoutBoundary`（把「read_timeout < 入口窗口 120s」「(retries+1)×read_timeout < 任务预算 300s」两条**不变式**钉成测试）与 `...ReadTimeoutOverride`（45/abc/0/空白），`...CompatibleWithGA` 探针扩展为断言 `read_timeout`/`max_retries` 真的落到真实 GA 客户端。验证：Go vet/build/全量 `-p 1`/race 5 关键包全绿。
- **Changes（第一轮）**：`llmcore.py` — `_post` 拆 `_post_once`（单轮 429/5xx 退避）+ 协商循环；新增 `_IMAGE_GEN_PARAM_TRIM_STATUS/_MAX_PARAM_TRIMS/_TRIMMABLE/_PARAM_UNSUPPORTED_HINTS` 与 `_unsupported_param`、`sniff_image_format`；`_payload` 不再显式发默认 `png`；每次 HTTP 尝试发 payload 快照；`stream=True` 的 4xx 响应补 close。`ga.py` — 落盘扩展名以魔数为准 + 请求/实返不符时 `[Status] ℹ️` 明示。`assets/tools_schema{,_cn}.json` — size 去 OpenAI-only 枚举、quality/output_format 补队列差异说明、quality 补 120s 窗口提示、model 补 503 语义。`tests/test_image_gen.py` — 30→44（协商 7 + 嗅探 5 + 落盘 2，含"不裁 size/n""防误裁""预算有界"边界）。`mykey.py`（本地）— 生图模型改 `agnes-image-2.5-flash` + 渠道2 key + `read_timeout=100`。文档 — `PHASE_B_IMAGE_GEN_PLAN.zh-CN.md` §7 补注 + 新增 §9.9；`tools.md` 生图条目补 ⑥-⑪；`memory.md` 基线 + 活跃窗口。
- **Insights**：
  - **"OpenAI 兼容协议"是接口壳，不是参数契约**：同一个中转网关后面挂着按"队列"划分的多上游，参数支持是**队列能力**而非协议规范——agnes 拒 `output_format/quality`，gpt-image 恰好接受同一个 `output_format`。所以"参数全集无条件下发"的设计假设必然在换模型时炸；而"按模型名加黑名单"又违反方案 §4 原则且永远追不上上游变化。**正解是把 4xx 当协商信号**：谁能接受的差异由上游自己用错误文本声明。
  - **自愈必须有诚实边界**：协商裁剪只允许动"缺席时上游有合理默认、且不改变用户可见契约"的可选参数（output_format/quality/…）；`size`（计费必传、模型必需）与 `n`（张数属用户契约，静默缩水=不诚实）**刻意不裁**——宁可把错误如实回给模型让它改参。**"能自愈"和"该自愈"是两件事**。
  - **防误裁靠三重门槛而非正则花活**：话术族命中 + 参数名在错误文本里字面出现 + 参数确在本次 payload 中。只靠"错误里提到某个词就删参数"会把 `prompt too long` 之类无关 400 误判成参数问题。
  - **默认值是最便宜的兼容性武器（第二例）**：08-14 的结论是"size 必传 → 客户端补默认 1024x1024"；本次是反面——`png` 本来就是协议默认输出格式，**显式发它只是给上游多一个 400 借口**。默认值该补的补、该省的省，判断标准是"不发会不会改变语义"。
  - **裁剪参数会让下游契约漂移**：一旦 `output_format` 被裁掉，请求 jpeg 也可能拿回 png ——旧实现会写出"名叫 .jpeg 的 png"，到 IM 侧就是 MIME 失配（与 08-14 微信生图死信事故同源）。**任何"上游可能忽略请求参数"的设计，都必须把产物属性从"请求值"改为"实测值"**（魔数嗅探）。
  - **故障面要分清，否则排错方向全错**：参数 400（队列不支持）与渠道 503（key/分组里没有该模型）都会表现为"生图不行"，但根因完全不同。**先 `GET /v1/models` 用同一把 key 自查模型可见性，比猜参数快一个数量级**——本次两步就分流了。
  - **基础设施的隐藏硬约束会以"别人的报错"出现**：网关在 Cloudflare 后面、proxy read timeout=120s，慢模型（gpt-image-2 实测 24-125s）就会以 **524 + HTML 响应体**的形式失败，看起来像"上游 5xx"。客户端 read_timeout 设成 100s（< CF 窗口）比设 300s 更好：宁可自己拿到干净的超时错误，也不要等 CF 把 HTML 灌进 JSON 解析路径。
  - **超时不是「填个够大的值」，而是从外部硬边界倒推**：同一个 `read_timeout` 同时被两个约束夹住——**下界**由上游真实耗时（agnes 8-11s）决定，**上界**由入口代理窗口（CF 120s：超了拿到的是 HTML 524，不是可判读的超时，重试全白烧）与**任务总预算**（300s：(retries+1)×read_timeout 必须留在预算内，否则任务被杀 → 零回复）决定。协议默认值（120s）恰好落在窗口边界上，是这次"看起来没配置"却必踩的坑——**默认值也需要与部署边界对账**。
  - **把不变式写成测试，而不是写成注释**："read_timeout < 入口窗口"、"最坏墙钟 < 任务预算"这类跨系统算术极易被后人随手调一个数字破坏；`TestBuildRuntimeConfigImageGenTimeoutBoundary` 让"调大就红"。同理，**配置字段必须验证真的被消费方读到**（GA 探针从断言 class/model 扩展到 read_timeout/max_retries），否则"写进 JSON 了"和"生效了"是两件事。
  - **「错误文本驱动自愈」必须先问：这段文本真的会到我手上吗？**（本次最大教训）客户端参数协商在本地/直连实测完美，一到托管形态就成了死代码——因为链路上有一层**出于安全考虑的清洗**（llm-proxy 把上游 400 体统一改写成 `UPSTREAM_ERROR`，理由是上游体可能含账号/配额）。**自愈能力依赖信息的可达性，而信息可达性常被代理层的安全/健壮性设计主动削弱**；两侧都要做：让该透传的信息**以最小必要形式**透过去（只取 message 重建，而非原样转发），同时让客户端具备**不依赖该信息也能退一步**的能力（保守参数集兜底）。只做一侧：要么留安全缺口，要么留死代码。
  - **「任务 succeeded」不等于「功能正常」**：本次三次任务全部 `succeeded` 且有图交付，但转录里模型在盲重试、并对用户说「图片服务不可用」——**失败诚实只保证「不静默」，不保证「不浪费」**。判断功能健康要看**模型侧看到什么**（backend_history 的 tool_result），而不是只看任务终态与交付记录。
  - **用户的一句「试了」是最强的验证输入**：这次不是单元测试发现的，而是**生产转录取证**（bundle.agent_history/backend_history + llm-proxy WARN 日志 + task_deliveries）把「模型盲重试 4 次」抓出来。**测试能证明代码按设计工作，生产转录才能证明设计是否成立**。
  - **"网关不支持"必须拆成三层定位，不能当成一句话结论**（2026-09-13 查证）：用户问"我这个不支持改图吗"，正确答案不是"支持/不支持"，而是三层各自的判定——① **上游有没有这个能力**（Agnes 官方改图是 `extra_body.image`，根本没有 `/images/edits`）；② **网关转发不转发**（new-api 的图片中继把请求反序列化进它的 `ImageRequest` DTO，**DTO 里没有的字段一律静默丢弃** → `extra_body`/`ratio`/`return_base64` 全部无声消失）；③ **网关有没有可用渠道/适配器**（`/images/edits` 路由存在、官方文档也有，但本实例 `abilities` 表里没有对应图像模型、上游对 edits 端点回 no available server）。**只查一层就会得出错误结论**：查路由→"支持"，查实测→"不支持"。
  - **静默无效参数比报错危险得多**：`extra_body.image` 传一个**不存在的图片 URL** 仍然 200 出图（说明参数根本没到上游）。若照着官方文档直接实现"参考图"，用户会得到一张毫不相干、却显示"成功"的图。**判定方法：给一个必然失败的合法输入，看上游是否抗议**——这是分辨"真支持"与"被丢弃"的最快手段，也应成为以后接入任何新通道的验收动作（写进 `.tasks/image-capability/DESIGN.zh-CN.md` §4.2 规则）。
  - **官方文档写的能力 ≠ 你这条链路上的能力**：文档给的 `ratio` 在实测里被丢弃，文档给的尺寸表却**真的有效**（`1312x736` 原样 16:9），而文档没强调的"归一化"行为（`1920x1080`→`1312x736`）反而要写进工具契约。**结论：文档只用来生成待验证清单，真值以实测矩阵为准**（矩阵见设计文档 §2）。
  - **"静默丢参"要定位到源码，不要停在行为反推**（2026-09-13，new-api）：此前只从行为推断"网关把字段丢了"；抓到源码后机制更精确——`dto.ImageRequest.UnmarshalJSON` 把未知字段**收进 `Extra`**（不是丢），而 `MarshalJSON` 合并 `Extra` 的循环**被注释掉**（旁注"不能合并ExtraFields"）→ 所以这是**有意设计**，不是 bug；同时 DTO 字段表给出了"能过网关的参数白名单"。**行为告诉我们"没生效"，源码告诉我们"为什么、以及哪些能生效"**；接新网关/新通道时，这份白名单比官方文档更可信。
  - **能力矩阵必须连同"探测所用凭据"一起记录**：本轮我把生产 `image_gen` 的 key 换成渠道2 之后，又拿它去试 gemini/gpt-image，得到 503 "no available channel ... under group free" 并据此写下"改图不可用"——**错的是凭据，不是渠道**。以后矩阵每行都要能回答"用哪把 key/哪个分组测的"，否则否定结论会把真能力误杀（也解释了为什么"先分诊再花钱"要放在最前）。
  - **"HTTP 200 就算成功"是错的验收标准**：判参考图是否真生效靠**像素/内容客观断言**（参考图中心蓝方块 → 输出中心变绿），而不是状态码——因为这条链路上"参数被静默丢弃 + 200 出图"是常态（`extra_body.image` 传不存在的 URL 仍 200）。同理，改图返回 JPEG 而非请求的 png 时，**魔数嗅探**保证了交付文件与真实字节一致（否则就是"名叫 .png 的 jpeg"）。
  - **同一个网关后面，不同上游的"同一接口"参数形态可能完全不同——这是"参数差异报错"的主因之一**（2026-09-13 实证）：`/v1/images/edits` 在 OpenAI 语义下是 **multipart 文件上传**，而 SenseNova 的同一个路径要 **JSON + `images:[{image_url}]`**；我们把 multipart 发给 SenseNova 得到的是上游 `invalid arguments`（不是 404/503，很容易被误判成"参数值写错了"）。**结论：接任何"看起来是同一协议"的上游，先按官方文档核对请求形态（endpoint/Content-Type/字段名/图片载体），再写代码**；客户端因此把"形态"做成显式 protocol 取值，而不是靠猜或靠重试。
  - **图片载体的可达性决定架构**：SenseNova 只接受**公网 URL 或带前缀 Data-URL**（不收纯 base64），我们没有公网图床 → 只能内联 Data-URL；而内联又撞上托管链路 `llm-proxy` 的 4MiB 请求体上限 → **"参考图怎么进沙箱"成为托管形态的前置设计问题**（降采样 / 受控上传换短时 URL / 抬上限）。**一个"免费模型"能不能用，往往取决于传输与沙箱约束，而不是模型能力本身。**
  - **"免费但慢"与"付费但快"必须都留在配置里而不是二选一**：sensenova 改图免费但 ~50s，gemini flash 9s 但要钱；把两者做成可切换的配置（并写清超时预算：read_timeout=110 < CF 120s 窗口；最坏 2×110 < 300s 任务预算），运营侧才能按"钱/时间"自己取舍——这正是"能力=通道属性，配置决定取舍"的设计意图。
  - **用户说的"日志"可能不在仓库里**：先按"复现"而不是"找文件"推进——`temp/` 只有测试产物，但真实 key 一测就把 400 的原文拿到手了。
