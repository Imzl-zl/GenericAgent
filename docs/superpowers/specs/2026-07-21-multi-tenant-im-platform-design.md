# 多租户 IM 个人助手平台 — 需求规格（PRD）

**日期：** 2026-07-23  
**状态：** 需求已收敛；已补充 2 vCPU / 4 GiB 验证基线与资源/运维约束；等待实现计划  
**架构约束：** [2026-07-21-multi-tenant-architecture.md](2026-07-21-multi-tenant-architecture.md)

---

## 1. 产品目标

在一台 Linux 服务器上，为约 10–20 名已批准用户提供个人 AI 助手。每位用户在 Web 端完成注册、人工审批、扫码绑定微信 bot 和人设/provider 配置；AI 对话发生在微信中（后续扩展至 QQ、飞书、钉钉等 IM 平台），Web 端仅做管理面，不承担对话职能。后续可创建团队并共享团队助手工作区。

用户可以要求助手处理工作区中的文档、运行 Shell/Python 自动化任务，但这不等于用户获得服务器权限：代码只能在所属会话的隔离 Worker 中执行。

### 1.1 核心原则

1. **个人优先：** 不创建团队也必须完整可用。
2. **隔离优先：** 私人工作区、团队工作区、平台控制面和宿主机是不同边界。
3. **默认拒绝：** 新账号默认未批准；未绑定或未批准身份不能消耗模型或启动任务。
4. **一人一 bot：** iLink 1:1；平台不提供共享 bot 多好友模式。
5. **Shell/Python 受控：** 允许自动化和文档处理，但只在会话 Worker 内执行。
6. **团队是共享空间：** 团队成员共享团队 history、working 和文件；私人信息不应放入团队会话。
7. **中继不是团队：** 跨 bot 文字中继不调用 AI，也不共享助手上下文。

## 2. 范围与分期

| 阶段 | 用户可感知的结果 |
|---|---|
| **P0：个人闭环** | 注册、人工批准、扫码绑定、个人人设、私人对话、隔离文件/Shell/Python、`/stop`、`/new`、崩溃后恢复已完成对话 |
| **P1：团队与中继** | 团队创建、双确认邀请、成员人设、团队共享工作区、`/个人`/`/团队`、跨 bot 文字中继、最小 Owner Web UI（人设分配与文件写权限配置） |
| **P2：增强运营** | 完整管理员 UI、多 IM（QQ/飞书/钉钉/企业微信/Telegram）、用量展示、人设/表情广场、定时任务、细粒度团队权限 |

P0 的试运行目标是约 10–20 人，不是容量承诺。实际并发上限由部署前压测和服务器资源确定。
当前 P0 容量验证基线为 2 vCPU / 4 GiB RAM；该基线用于压测和部署配置，不代表固定活跃人数、并发数或响应时间。更换主机规格、存储或运行时后必须重新压测。

## 3. 用户与权限

| 角色 | 能力 |
|---|---|
| 平台运营者 | 批准、封禁、解除绑定、查看必要审计；P0 可用受保护的最小管理操作，不要求完整后台 UI |
| 终端用户 | 注册、绑定自己的微信 bot、使用私人助手、加入团队 |
| 团队 Owner | 创建团队、直接邀请或审核邀请码申请、分配成员人设、移除成员、管理团队文件写权限 |
| 团队成员 | 经双确认加入团队后使用团队助手；不得自行更改 Owner 分配的人设 |

账号状态固定为 `pending`、`approved`、`blocked`：

- 注册后默认 `pending`。
- 只有 `approved` 可绑定、运行任务或进入团队。
- `blocked` 立即失去会话和任务权限；进行中的任务由平台取消并审计。

## 4. P0 功能需求

### 4.1 账号与准入

| ID | 需求 |
|---|---|
| A1 | 用户可用唯一用户名和密码注册；密码必须安全哈希保存 |
| A2 | 新账号默认 `pending`；平台运营者必须显式批准 |
| A3 | 未批准用户可登录查看审批状态，但不能绑定 bot、调用模型或启动 Worker |
| A4 | 运营者可封禁账号；封禁立即阻断后续消息与任务 |
| A5 | P0 提供可审计的最小批准/封禁操作；完整管理员 Web UI 属于 P2 |
| A6 | 平台运营者可通过受保护的运营操作调整运行时调度配置；修改范围受部署硬上限约束，变更必须记录 actor、原因和版本；P0 不要求完整管理员 Web UI |

### 4.2 微信绑定与身份

| ID | 需求 |
|---|---|
| X1 | 一个平台用户只能绑定一个微信 bot；重新绑定显式覆盖旧绑定 |
| X2 | 用户在 Web 发起绑定，扫码获得 iLink bot token 与 bot UUID |
| X3 | 二维码扫码确认即完成绑定，iLink 官方流程在 `confirmed` 时返回 `ilink_bot_id`/`bot_token`/`ilink_user_id`/`baseurl` 顶层字段，无需额外 `/activate` 步骤（见 [iLink 绑定流程 SPEC](2026-07-25-ilink-official-binding-flow.md)） |
| X4 | 只有消息 bot UUID 与已配对 `from_user_id` 同时匹配时，消息才属于该平台用户 |
| X5 | token 过期时，显示重新绑定指引；不得影响其他 bot 的轮询或状态 |
| X6 | 每个 bot 的 token、update cursor 与 context token 独立保存，平台不使用共享本地 token 文件 |
| X7 | `/我的身份` 显示用户名、账号状态、当前个人/团队上下文与 bot 状态 |

### 4.3 个人助手与工作区

| ID | 需求 |
|---|---|
| G1 | 每位已批准用户拥有独立个人工作区、history、working、文件和人设 |
| G2 | 用户可在 Web 编辑自己的默认人设；人设仅影响自己的个人会话 |
| G3 | 助手可在当前工作区读取、写入和处理文件 |
| G4 | 助手可在当前会话的隔离 Worker 内运行 Shell/Python 完成文档解析和自动化 |
| G5 | Shell/Python 不得读取宿主机、平台秘密或其他工作区；默认无任意公网访问 |
| G6 | `/stop` 只取消调用者自己正在运行的任务；取消会保留当前工作区的半成品 |
| G7 | `/new` 创建当前工作区的新对话：清 history 与 working，不删除工作区文件，不生成额外快照；`/new` 后崩溃恢复到 `/new` 前最后一个成功 task 的快照 |
| G8 | 任务排队有上限；满额、超配额、上游限流或 Worker 故障必须明确告知用户 |

### 4.4 可靠性

| ID | 需求 |
|---|---|
| N1 | 每个成功完成的任务都先持久化完整会话快照与有上限的最终用户结果，再向用户报告完成 |
| N2 | 进程或 Worker 崩溃后，已完成任务的会话可恢复 |
| N3 | 崩溃时正在执行的 Shell/Python 任务标为中断，不自动重放 |
| N4 | 同一会话串行执行；不同会话可并行，具体上限由部署配置决定 |
| N5 | 相同 bot 的重复消息不得创建重复任务 |
| N6 | 快照文件与数据库状态分阶段提交并登记 writing/committed/quarantined 生命周期；活跃写入由控制面 lease 保护，orphan 经过 grace 与 quarantine 后延迟删除；任一崩溃窗口都恢复到最后一个 committed 快照，被终态 delivery 引用的结果在交付终态和结果保留期前不得清理 |
| N7 | LLM Proxy 或控制面重启必须产生可见错误和审计；成功、失败、取消和中断 task 都通过稳定 delivery_id 与持久化 delivery 状态重试终态通知，未确认 delivery 超过配置窗口进入 dead-letter，历史流式 chunk 不重放；carrier 不支持幂等时明确 at-least-once 风险，可能有副作用的运行中 task 不得自动重放 |

### 4.5 工具授权、文件保护与审计

| ID | 需求 |
|---|---|
| P1 | 平台采用“默认拒绝、按 capability 授权”；有效权限受平台永久拒绝、部署策略、用户/团队授权和当前 session 状态共同限制 |
| P2 | P0 默认仅允许读取工作区输入、写入生成输出、受限 Shell/Python 和文档解析 |
| P3 | 上传原件只读；P0 不允许 Agent 删除原件或直接修改源文件 |
| P4 | 修改/删除源文件、团队文件写入、受控网络、外部 API、高资源配额属于高风险 capability，必须显式授权、记录理由和到期时间 |
| P5 | 高风险源文件变更必须生成影响清单，经用户确认后由平台原子应用或移入可恢复回收站；Shell 不得绕过该流程 |
| P6 | 宿主机、其他 workspace、真实 Key、数据库、容器 socket、提权和任意公网永久不可授权，即使团队 Owner 也不能开启 |
| P7 | 平台审计记录任务、工具权限决策、资源事件、策略拒绝、授权变更与模型用量；日志脱敏，不记录真实 Key 或完整敏感参数 |
| P8 | 检测和告警用于解释与追责，不能替代 Worker 隔离；系统必须先阻断秘密读取、跨租户访问和任意外传 |

### 4.6 性能与配额

| ID | 需求 |
|---|---|
| Q1 | 每 user/team 有独立任务队列和额度；单一用户不能耗尽全局 Worker 或模型并发 |
| Q2 | 平台限制任务时长、CPU、内存、PID、磁盘、输出字节、队列长度和模型 token；超限给出明确提示 |
| Q3 | 调度按同 session FIFO、跨租户公平配额执行；Worker 完成 checkpoint 后可进入 idle 复用，超时或资源压力下销毁 |
| Q4 | 所有配额数值由服务器压测后写入部署配置；PRD 不承诺未经验证的并发数或性能指标 |
| Q5 | 全局准入不能只看 Worker 数量；必须用 cgroup `memory.current` 实时内存占用、starting/task 静态预留和目标主机预算共同判断，指标缺失时保守回退，并同时检查 CPU、PID、磁盘、模型并发和租户额度；swap 不计入容量且策略须显式验证 |
| Q6 | Worker 进入 idle 前已经完成 checkpoint；Worker Manager 用互斥的 idle→assigned/idle→evicting 状态转移处理复用与压力淘汰，资源压力升高时直接淘汰 idle Worker，不重复 checkpoint，不得等待宿主机 OOM；资源不足时明确排队或拒绝，idle 复用不是容量保证 |
| Q7 | history、working、display history、task output、最终结果/终态错误 payload、tool stdout 和 snapshot 都有部署级字节上限；上限在数据累积过程中生效，超限必须可见失败且保留最后成功快照 |
| Q8 | P0 应用进程和 LLM Proxy 具备健康检查与失败自动重启；审计/结构化日志轮转、保留期、磁盘告警和 PostgreSQL 资源配置均属于部署门槛 |
| Q9 | 平台运营者可运行时调整全局同时运行 task 上限；调低不强杀运行中 task，调高唤醒 queued task，设置为 0 进入 drain/维护模式 |
| Q10 | 超过运行并发上限的 task 必须持久化排队，按同 session FIFO 和跨租户公平调度；服务重启不丢 queued task，不重复领取 |
| Q11 | P0 任务排队不依赖外部消息队列；PostgreSQL 是任务事实来源，唤醒通知丢失时仍能通过周期扫描恢复 |

## 5. P1 团队模式

团队是独立共享工作区，不是多个私人助手的拼接。

| ID | 需求 |
|---|---|
| T1 | 已批准用户可创建团队；Owner 自动成为已批准成员 |
| T2 | Owner 可生成邀请码；用户主动输入邀请码后，Owner 批准才可加入 |
| T3 | Owner 可直接邀请已注册用户；成员接受后，Owner 再批准，才成为成员 |
| T4 | 已批准成员可用 `/团队 <名称>` 进入团队上下文，用 `/个人` 回到私人上下文 |
| T5 | 团队成员共享团队 history、working、文件和 cwd；成员默认不能读 Owner 的私人工作区 |
| T6 | Owner 可为每位成员分配人设；回退顺序为成员人设、团队默认人设、平台默认人设 |
| T7 | 团队会话中的 `key_info` 对全体团队成员可见；用户不得在团队会话输入不希望成员看到的私人敏感信息 |
| T8 | Owner 移除成员后，成员下一条消息即不能进入团队；正在运行的成员任务按平台策略取消并审计 |
| T9 | P1 默认仅 Owner 可写团队文件；成员可读已授权内容。未来可增加显式写入开关 |

## 6. P1 跨 bot 文字中继

| ID | 需求 |
|---|---|
| R1 | 仅双方均已批准、已绑定且接收方未 opt-out 时，允许转发；接收方可用 `/relay_off` 拒收 |
| R2 | `@username <消息内容>` 直接转发给目标用户的微信；整条 `@username` 无消息内容时提示用法 |
| R3 | 转发消息带发送人前缀（`[来自 X 的消息] <内容>`），不调用 AI，不进入 task 队列 |
| R4 | 仅个人上下文触发转发；团队上下文里 `@username` 作为普通消息给 AI，不外传 |
| R5 | 中继仅支持文字；图片、语音和文件明确提示不支持 |
| R6 | 默认不记录中继正文，只审计双方、时间、状态和长度到 `audit_events` |
| R7 | 每条转发独立无状态；`/relay_on`/`/relay_off` 控制接收偏好，立即生效 |

转发设计为无状态直接投递（Direct Forward），不引入邀请/同意/短 ID 状态机：微信传话场景以零星一次性为主，持续对话用户会直接加微信好友；无状态方案 O(1) 查偏好即可投递，无并发风险，符合 Slack/Discord/Telegram @mention + 消息的通用习惯。

## 7. 命令与消息规则

| 命令/消息 | 行为 |
|---|---|
| `/activate <code>` | 已废弃。iLink 官方扫码流程在 `confirmed` 时直接完成绑定，无需此命令（保留只为向后兼容旧文档引用） |
| `/我的身份` | 查询身份绑定、账号状态、当前个人/团队上下文、bot 状态 |
| `/状态` | 查询当前 session 的任务队列、资源用量与上下文状态 |
| `/个人` | 切换至私人上下文 |
| `/团队 [名称]` | 进入指定已批准团队；无名称时列出可进入团队 |
| `/邀请码 <code>` | 用户提交团队邀请码，创建 `pending_owner` 申请等待 Owner 批准；可经 Web 表单或 IM 提交 |
| `/同意 t-456` | 成员接受直接团队邀请（仅 `pending_member` 状态有效） |
| `/批准 t-456` | Owner 批准待批准的成员加入申请（仅 `pending_owner` 状态有效） |
| `/拒绝 t-456` | 任一方拒绝团队邀请，按发送者角色解释 |
| `/移除 @username` | Owner 移除团队成员，立即生效 |
| `/relay_on` | 开启 `@username` 转发接收（默认开启） |
| `/relay_off` | 关闭 `@username` 转发接收，立即生效 |
| `/stop` | 仅取消自己正在运行的 task |
| `/new` | 清当前 session 的 history 与 working，不删除工作区文件，不生成额外快照 |
| `@username <消息内容>` | 个人上下文下直接转发给目标 bot；团队上下文里作为普通消息给 AI |

平台命令优先于 AI。转发消息不进入 AI、不进 task 队列。命令优先级见架构 §6.2。

## 8. 安全与隐私要求

| ID | 需求 |
|---|---|
| S1 | 用户与团队工作区必须由 OS 级 Worker 隔离；路径过滤仅是附加防御 |
| S2 | 未绑定、身份不匹配、未批准或已封禁消息不得消耗他人助手 |
| S3 | 真实模型 API Key、bot token、数据库凭证不得进入 Worker 或出现在模型输出/日志中 |
| S4 | bot token、cursor 和 context token 加密存储，并具备密钥轮换版本 |
| S5 | Worker 无容器管理 socket、宿主机目录、任意网络和提权能力 |
| S6 | 每次团队进入都复核成员关系；缓存不得绕过移除或封禁 |
| S7 | 操作审计记录认证、绑定、批准、任务、取消、策略拒绝和密钥访问，不默认存储敏感中继正文 |
| S8 | 微信/iLink 的可达性、条款和协议风险需由运营方评估；产品不承诺零风险 |

## 9. 验收标准

### P0

1. 已批准用户可完成注册 → 批准 → 扫码绑定 → 私人对话的闭环。
2. 未批准、未绑定或来自不匹配 `from_user_id` 的消息不能创建 task。
3. A 的 Worker 不能读 B 的文件、history、working、输出、token 或宿主机路径。
4. Shell/Python 在 A 的工作区内成功处理文档，但无法访问容器管理 socket 或真实平台 Key。
5. A 的 `/stop` 不影响 B，也不影响团队中其他成员请求的 task。
6. 每个完成任务重启后保留 history 与 working；崩溃中的 task 不自动重复执行。
7. 多 bot token/cursor 独立；一个 token 过期不会破坏其他 bot。
8. 资源或队列不足时，用户获得明确失败/等待提示，系统产生审计事件。
9. 资源准入使用 cgroup `memory.current` 实时占用、starting/task 预留和主机预算；指标缺失时保守回退。压力下直接淘汰已经 checkpoint 的 idle Worker，不重复 checkpoint，也不等待宿主机 OOM；用户能区分排队、配额不足和资源不足。
10. history、输出、工具 stdout 或 snapshot 超过部署上限时，限制在累积过程中生效，任务不会被报告为成功，最后一个成功快照仍可恢复。
11. 快照 lease、文件提交、数据库提交、`task_deliveries`、终态发送和 LLM Proxy 重启等故障窗口均可恢复：系统使用最后一个 committed 快照，按稳定 delivery_id 重试成功/失败/取消/中断终态，超过 `DELIVERY_RETRY_WINDOW` 才 dead-letter；`TASK_RESULT_RETENTION` 到期前保留结果，历史 chunk 不重放，carrier 确认前的 at-least-once 风险可见且不自动重放可能有副作用的任务。 
12. 平台运营者调整并发配置时，系统校验部署硬上限并记录 actor、原因、旧值、新值和 config version。
13. 超过全局或租户运行上限的 task 进入持久化队列；同 session FIFO、跨租户公平、队列满和重启恢复行为可验证。
14. 调低并发不强杀运行中 task，调高并发会唤醒 queued task；设置为 0 时不启动新 task，已排队任务不丢失。

### P1

15. 团队成员使用不同分配人设时，排队执行仍使用各自 task 的 persona。
16. 被移除成员不能再次进入团队；其私人会话不受影响。
17. 团队成员理解并验证团队 `key_info` 共享边界。
18. `@username <消息内容>` → 直接转发给目标 bot，不调 AI，不进 task 队列；接收方 `/relay_off` 拒收；团队上下文里 `@username` 作为普通消息给 AI。

## 10. 当前不做

- 平台共享 bot 多好友、微信群 bot、图片/语音中继。
- 任意公网 Shell、宿主机桌面键鼠控制、用户自定义容器镜像。
- 未经压测的并发容量宣传。
- 自动重放崩溃时可能执行过副作用的任务。
- 把团队工作区当私人工作区。
- 未经独立安全评审，不把 nsjail、bubblewrap 或其他轻量沙箱直接当作 rootless Podman 的等价替代。
- P0 不引入 RabbitMQ、Redis、Celery 等外部消息队列作为任务事实来源；任务排队由 PostgreSQL 持久化。
